## External compatibility constraints reviewed 2026-09-28

The public platform APIs do not provide one portable contract for this browser
extension. Google’s Library API is limited to media and albums created by the
app, while user-selected content belongs in the Picker flow; the extension’s
Google adapter therefore stays page-bound and must keep its private-route
validation and fail-closed coverage checks ([Google list guide](https://developers.google.com/photos/library/guides/list), [Google Photos API updates](https://developers.google.com/photos/support/updates)).

Apple’s supported application-level route is PhotoKit, which requires a native
app authorization and exposes persistent change tokens; CloudKit JS requires an
app container and token. A Chrome extension cannot use those native APIs as a
drop-in iCloud Photos library API, so the iCloud adapter must treat the signed-in
Photos page and its private CloudKit session as a compatibility boundary, keep
`PrimarySync` personal-library scope explicit, and fail closed when the session or
record schema is uncertain ([PhotoKit](https://developer.apple.com/documentation/PhotoKit), [persistent changes](https://developer.apple.com/documentation/photos/phphotolibrary?language=objc), [CloudKit JS](https://developer.apple.com/documentation/cloudkitjs/cloudkit)).

The open-source rclone implementation provides a useful independent schema
cross-check: `PrimarySync` and `SharedSync-*` are separate photo libraries, while
`CMM-*` zones are shared-album zones without a usable `CPLAlbumByPositionLive`
index. That supports the current decision to query only `PrimarySync` and label
returned albums as personal until shared-library ownership and mutation semantics
are proven ([rclone iCloud Photos implementation](https://github.com/rclone/rclone/blob/master/backend/iclouddrive/api/photos.go)).

Apple documents CloudKit sync tokens as opaque change-history markers and defines
zone-change pagination through `moreComing` ([CloudKit record-zone changes](https://developer.apple.com/documentation/cloudkit/ckdatabase/fetchrecordzonechanges%28inzonewith%3Asince%3Adesiredkeys%3Aresultslimit%3Acompletionhandler%3A)). The use of `PrimarySync`, iCloud Photos' private record schema, and token compatibility between its `records/query` and `changes/zone` routes comes from reverse-engineered community work, not an Apple-supported Photos contract ([kei sync-token reference](https://github.com/rhoopr/kei/blob/main/docs/synctoken-reference.md)). PhotoSweep therefore treats that route as an optimization: it reuses a same-session complete snapshot only after a structurally exact empty change response. Any changed, paginated, invalid, or malformed response triggers a full scan. Local contract proof does not establish live provider convergence.

A read-only inspection of the signed-in Amazon Photos page’s account menu exposed
the account display name and navigation controls but no email address. The
adapter independently binds the provider page to an opaque owner marker, rotates
the opaque session ID when that marker changes, and persists only its SHA-256
fingerprint. The user-facing identity therefore remains `session_only`; the
adapter must not invent an email identity from a display name.

Login with Amazon offers a separate identity route: `profile:user_id` returns an
Amazon account ID scoped to the relying application, while the `profile` scope
also returns the account name and email and requires customer consent
([Customer Profile](https://developer.amazon.com/docs/login-with-amazon/customer-profile.html)).
Amazon recommends the Authorization Code Grant for new integrations; that flow
requires PKCE for browser-based apps. The JavaScript SDK's browser flow stores
the PKCE verifier in a same-origin cookie and exposes the access token and its
expiry; Amazon's general token documentation says a refresh token may be issued,
so a refresh-token guarantee must not be assumed for an extension client
([JavaScript SDK reference](https://developer.amazon.com/docs/login-with-amazon/javascript-sdk-reference.html),
[access tokens](https://developer.amazon.com/docs/login-with-amazon/access-token.html)).
A server-side exchange can keep tokens off the client and support refresh
([Authorization Code Grant](https://developer.amazon.com/docs/login-with-amazon/authorization-code-grant.html)).
The Implicit Grant is no longer available for new security profiles
([deprecation details](https://developer.amazon.com/docs/login-with-amazon/implicit-grant.html)).
PhotoSweep does not currently run a separate Login with Amazon flow. It could
provide a documented per-application account ID, and an explicitly consented
`profile` scope could also provide email, but either path adds a separate sign-in
and token lifecycle. The active parity objective makes email identity an open
product requirement. However, Login with Amazon's app-scoped customer ID has no
documented crosswalk to Amazon Photos' private owner marker, so its email cannot
yet be presented as the identity of the open Photos session. No LWA client or
redirect configuration exists in this repository. Before implementing this
route, register and configure a security profile, validate its PKCE redirect
from the extension, obtain explicit `profile` consent, and prove that its
customer identity maps to the Photos owner marker for the same test account.
Keep the existing owner-marker session binding authoritative until that link is
proven. Independently, exact-current live Aside evidence is still required for
the existing account-switch guard.

## Completion rule

Track each provider and scenario independently. A row passes only when current direct evidence is tied to the exact source, extension build, provider, provider session, selected album, and disposable fixture. A local adapter test cannot pass a live-provider row. A prior six-item round trip cannot pass a different pagination, empty-album, nested-album, media/date, or account-transition row.

Use these row outcomes:

- **PASS:** fresh evidence meets every scenario assertion, including exact membership and proven traversal exhaustion where the scenario requires it.
- **PARTIAL:** evidence is fresh and internally consistent, but one or more pages, records, media classes, or transitions remain unobserved. The scenario does not count as complete and cannot satisfy an aggregate PASS.
- **BLOCKED:** required evidence is missing, stale, unbound, contradictory, inaccessible, or the needed disposable session is unavailable. Missing evidence must never be converted to an empty result or a PASS.

The existing aggregate evidence engine accepts PASS, FAIL, or BLOCKED. Until it has an explicit PARTIAL aggregation rule, a scenario recorded as PARTIAL must be represented as BLOCKED at the aggregate gate with its partial evidence path and remaining assertion stated. It must not be silently omitted.

## Shared evidence contract

The legacy destructive round-trip record uses schema version 1. Current exact-package destructive evidence uses schema version 2 and also carries the runtime build ID and package ZIP SHA-256. Its live binding continues to require a nonempty synthetic inventory, one target in that inventory, and a distinct keeper in that inventory. Empty albums cannot satisfy that destructive contract.

Read-only album scans use schema version 3 for exact-package evidence in `verification/live-provider-evidence.mjs`. Legacy schema-v2 observations remain readable for historical comparisons, but cannot satisfy a current package gate. The validator accepts zero members only for a named non-destructive scenario with:

- Synthetic-fixture identity and exact provider, account, opaque session, and album binding.
- Runtime extension ID, current package version, service-worker-owned build ID, current source fingerprint, and ZIP SHA-256 matching the package sidecar.
- A personal, non-shared selected album found in the album listing.
- Listing and membership page counts plus explicit cursor-exhaustion booleans.
- Exact membership IDs and provider-reported membership count when membership is exhausted.
- Unique visited, returned, and skipped IDs whose counts reconcile and whose sets partition visited IDs.
- `complete: true` only with `stopReason: "exhausted"`, listing exhaustion, membership exhaustion, and exact membership reconciliation.
- An explicit `mutation.attempted: false`; Trash or restore fields are rejected for a read-only scenario.

A valid but incomplete schema-v3 record can be `PARTIAL`; it cannot be used as PASS evidence. An absent or stale runtime/build/source/package/session/scope binding, contradictory counts, missing completion state, or unsupported schema is `BLOCKED`. Read-only schema versions are not a fallback for the destructive schema, and the destructive validator still requires the target/keeper inventory.

## Run protocol and artifact layout

1. Run local property and adapter checks first. Bind every result to the fresh source fingerprint from that run.
2. Use only disposable synthetic accounts and albums. Never use a personal library for destructive evidence. Empty and pagination scenarios are read-only.
3. Capture the expected album/member inventory before scanning. Save only sanitized page summaries, stable synthetic item IDs, page counts, cursor exhaustion, coverage counts, and runtime provenance. Do not save cookies, authorization headers, cursor secrets, private media, or stable account identifiers.
4. Store each run beneath `tmp/verification/<UTC-run-id>/`; use one artifact per scenario row and include the exact `scenarioId`, `provider`, `sessionId`, `albumId`, extension version, and source fingerprint.
5. Keep implementation tests, disposable live-provider runs, and release/package gates as separate proof classes. Do not substitute a local page mock for provider traversal evidence.
6. Re-run the relevant local formal gate after any code or scenario-validator change. If source changes during a run, invalidate its evidence and repeat against the final fingerprint.
