## Evidence rules

- Keep every requirement below in scope. A provider capability that is absent, unknown, unsupported, or unproven stays explicitly so; parity must not be reduced to the existing common denominator.
- Record each property with a bounded claim, proof class, exact verifier or observation, pass condition, actual result, durable evidence path, and `PASS`, `FAIL`, or `BLOCKED` verdict. `PARTIAL` live evidence is recorded with its artifact and remaining assertions, and is `BLOCKED` at an aggregate gate.
- Local static/test/build proof, browser runtime proof, provider/account proof, package proof, and rollout/store/production proof are separate evidence classes. A test does not pass a live-provider row.
- Bind any live observation to extension ID/version, build ID, package ZIP SHA-256, source fingerprint, provider, provider session/account as available, exact scope/album and fixture inventory. Sanitize logs; never store cookies, bearer tokens, private media, or unsanitized stable account identifiers.
- Trash/restore evidence is limited to a specifically authorized disposable synthetic fixture. No real-library Trash or restore is authorized by this engineering request.

At the app boundary, a complete terminal may reconcile provisional unknown restore progress only while its exact request ID remains in the current page's in-memory request map. Reload clears that binding, so a held reply from the old page leaves recovery unknown. The lower-level recovery-history reducer covers persisted request-ID matching only; it does not implement a reload lease. This is a scoped local contract assumption, not provider-side proof or a claim of remote atomicity.

The existing TLC/TLA abstraction covers the prior moved-subset/Undo safety model only. It has not been extended/refined to prove per-target failed/unknown/not-dispatched partitions, cumulative restore progress, malformed terminal coverage, or sticky restore history. Generated `SAFE-12` is executable refinement evidence through the actual `TrashLifecycle` and recovery-history reducer; it is not a TLC proof. ## Shared contract being integrated

The common scan flow covers library, inclusive local-calendar date range, personal album, and album-plus-date scopes; photo/video coverage; visit limits; complete/partial/failed/cancelled outcomes; progress; unique visited IDs; `visited = returned + skipped`; unknown-date accounting; session/scope-bound results, caches, checkpoints, resume, and recovery; incremental reuse/fallback; duplicate classification; review and keep decisions; preflight and exact-count confirmation; per-target Trash/restore; reports; and the configured plan limits and entitlement gates.

The adapter-neutral media record must preserve current fields and add truthful provenance rather than invent values. The frozen compatibility-preserving names are `mediaKind: "photo" | "video" | "live-photo" | "unknown"`, optional `mimeType`, canonical `duration` in milliseconds, `timestampProvenance: "capture" | "creation" | "modified" | "unknown"`, `creationTimestampProvenance: "creation" | "modified" | "capture" | "unknown"`, `favoriteStatus: "favorite" | "not-favorite" | "unknown"`, optional `favoriteSource: "provider-metadata" | "provider-lookup" | "unavailable"`, and optional `livePhotoAssociationId` only where a stable relationship is proven. Bare durations must not be unit-guessed by magnitude; adapters may normalize only a proven seconds or milliseconds source field. Keep legacy `isFavorite` only when the provider supplied an explicit boolean. Preserve known/unknown original-quality and quota fields, original-content identity evidence, and video playback capability. A Live Photo flag alone is not evidence that a separate still and motion record are associated. ## Codebase design review: favorite protection (2026-09-30)

- **Module/interface:** `favoriteStatusForItem(item)` is the shared normalization module. Its small interface maps legacy booleans and explicit status/source fields to `favorite`, `not-favorite`, or `unknown`, so review, reporting, and selection code do not parse provider payloads independently.
- **Seam/adapters:** Keep current-state reads and any concurrency check inside each provider's `trashItems` adapter. Google GPTK item info, Amazon exact-node reads, and iCloud CloudKit records have different version semantics; a generic version token in the shared media interface would leak provider details without supplying a common guarantee.
- **Depth/locality/leverage:** The shared normalizer gives the UI one status rule; provider adapters keep remote checks local. Current tests exercise all three command adapters and favorite review labels through their existing seams.
- **Verified limit:** The iCloud adapter sends `operationType: "update"` with the current asset `recordChangeTag`. Apple's [CloudKit record-change documentation](https://developer.apple.com/documentation/cloudkit/ckrecord/recordchangetag) describes compare-and-save for standard CloudKit records, but the Photos private route's native race test accepted a stale-tag Trash after the favorite changed. Google has the same check-then-dispatch window. These checks reduce the window; they do not prove atomic protection from concurrent provider changes.
- **Decision:** Keep the shared normalization and provider-owned checks. Do not add a shared abstraction that claims atomicity. `FAVORITE-PROTECTION` remains **BLOCKED** pending exact-candidate live proof of fresh pre-dispatch state, snapshot-bound unknown-state acknowledgement, and truthful outcomes on each provider. This is a best-effort point-in-time contract; do not claim concurrent-change atomicity.
